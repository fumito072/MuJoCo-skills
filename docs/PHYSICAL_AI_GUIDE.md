## 1. 前提知識ゼロからの基礎

### 1.1 物理シミュレーションとは / MuJoCo とは

**MuJoCo** は物理エンジンです。ロボットの形状・質量・関節・モーターを記述したモデル(XML)を
読み込み、0.002秒刻みで「次の瞬間に世界がどうなるか」(重力、慣性、接触、摩擦)を計算します。
ゲームの物理と違い、ロボット研究用に**接触と関節の精度**を重視して作られています。

なぜシミュレーションでやるのか:
- 実機のG1は数百万円で、転倒1回で壊れるリスクがある。シムでは1秒間に何千回でも転べる
- 「うまくいくか分からないアイデア」を分単位で試せる(本プロジェクトは1日で11回失敗して完成した)
- **シミュレーションで完成 → 実機はLinux機で検証**、という業界標準の開発順序(sim-first)

### 1.2 ロボットの体: 自由度(DOF)とアクチュエータ

G1 には **29個の関節**(=29 DOF)があります: 各脚6(股3+膝1+足首2)、腰3、各腕7。
それぞれに**ポジションアクチュエータ**(モーター)が付いていて、制御入力 `ctrl` は
「この関節をこの角度にせよ」という**目標角度**です。モーターはバネのように目標へ引っ張ります
(この強さが kp。重要な事実: **G1の足首は kp=20 で、股・膝の 75 に比べて非常に弱い**。
これが後述の多くのドラマの原因)。

体の位置・姿勢は `qpos` という配列に入っています。先頭7個が骨盤(浮遊ベース)の位置と向き、
残り29個が関節角度です。

### 1.3 「ポリシー」= ロボットの脳

**ポリシー**とは「観測(センサ値)→ 行動(モーター指令)」を毎ステップ計算する関数です。
本プロジェクトの歩行ポリシーは、DeepMind が強化学習(RL)で訓練した公式のニューラルネット
(`g1_joystick_29dof.onnx`、たった884KB)で、次のループを **50Hz** で回します:

```
観測103次元                              行動29次元
[体の速度・角速度・重力方向・           →  各関節の目標角度のオフセット
 指令(vx,vy,wz)・関節角・関節速度・        (ctrl = 基準姿勢 + 行動×0.5)
 前回の行動・歩行位相]
```

「指令(vx, vy, wz)」はゲームパッドのスティックと同じ意味です(前後速度・横速度・旋回速度)。
つまりこのポリシーは**ジョイスティックで操縦できる歩行スキル**で、私たちのコードは
「誰がスティックを倒すか」を自動化しているのです(後述のFSM)。

重要な性質(実測済み):
- 指令ゼロでも完全静止せず、その場で足踏みし続ける(止まる=転倒、を学習で避けている)
- **ポリシーを切って固まると約2秒で転倒する**(足首が弱く、能動バランスが必須)
- 後ろ向き歩行も可能(本E2Eで実証)

### 1.4 なぜ Mac だけでできるのか

学習(ニューラルネットの訓練)には通常 NVIDIA GPU が要りますが、**推論(訓練済みの脳を
動かすこと)は CPU で十分**です。本プロジェクトの方針は「**train once / infer local**」:
学習済みの脳を借りるか、必要ならクラウドGPUで1回だけ訓練し、**実行は常に Mac ローカル**。
M5 Max は物理シミュレーションを毎秒3.3万制御ステップ回せる(実測)ので、
将来必要なら CPU だけで強化学習さえ可能です(20Mステップ≈15-30分)。
(後日談: 段差登りという単発の難スキルでは Mac CPU の 2.5億ステップでも探索量が
足りず、学習だけ Colab GPU に出した — §1.5 と docs/FULL_MISSION_DEPLOY.md 参照。
「推論は常にローカル」の方針は変わっていない)

### 1.5 学習 → 検証 → 実行 — モデルはどこから来て、どこへ行くか

このプロジェクトのすべてのスキルは、次の3段階パイプラインを通る:

```
┌─ 学習(GPUがある場所)─────────┐   ┌─ 検証(Mac)──────────────┐   ┌─ 実行(体がある場所)─┐
│ 何百万回の試行錯誤。            │   │ 学習の成果物(重みファイル │   │ シム=フルミッション   │
│ 数千体を並列シミュレートして     │──▶│ 数MB)を読み込み、計測器   │──▶│ 実機=Linux PC上の    │
│ スキルを発見する                │   │ 付きで何十回も走らせて測る │   │ 同じコントローラ      │
└────────────────────────────┘   └──────────────────────────┘   └────────────────────┘
```

**「既製品があれば使う、なければ作る」** — 学習済みモデルは使い回せる(それが
重みファイルの良さ)。汎用の歩行は DeepMind の既製品をそのまま使っている(再学習
ゼロ)。一方「この椅子の0.22m台に登る」のような環境固有のスキルは世界の誰も作って
いないので、自分で学習させる(Colab GPU)。**なぜ学習だけGPUか**: 計算が速いから
ではなく、**数千体の並列試行錯誤=探索の量**が手に入るから(Mac CPU 10-12並列で
2.5億ステップ回しても「発見」できなかった、という実測が根拠)。

**なぜ学習と実行の間に「検証」を挟むのか**(直結してはいけない理由、全て実体験):

1. **学習環境は簡略化されている** — 速度のため、登り学習のシーンは椅子を「箱1個」に
   している。フル形状(153衝突メッシュ)でも技が通用するかは検証して初めて分かる
2. **学習中のスコアは嘘をつく** — 方策が報酬を「ハック」する事例を本プロジェクトで
   3回実測(縁に腰掛けて生存ボーナス回収/片足掛け農場/横に逃げて脚ポーズだけ
   真似る)。数字が高くても本当にやっているかはロールアウトの検証でしか分からない
3. **統合は部品の和ではない** — スキルはチェーン(回避→回頭→後退→登り→着座)の
   1ピースで、引き継ぎ部のバグは単体学習では絶対に出ない(§5の11連敗が証拠)
4. **実機の失敗は高い** — シムの転倒はタダ、実機の転倒は数百万円の破損リスク。
   物理の「実装」を変えても動くか(MJX→C engine の sim2sim)が、実機投入
   (sim2real)前の最も安いリハーサル

**検証と実行は「同じコードを動かす」が目的が違う**:

| | 検証 | 実行 |
|---|---|---|
| 目的 | **測る**(使えるかの判定材料を作る) | **達成する**(タスクそのもの) |
| 回数 | 何十回(条件をランダムに振る) | 1回 |
| 失敗 | 歓迎 — どの条件で落ちるかが収穫 | 困る |
| 計測 | テレメトリ・成功判定・統計だらけ | 身軽 |
| 出力 | 「20本中18本成功、ヨー±10°が限界」 | 座れた、という結果 |

例えるなら**模試と本番入試**(解く問題は同じ、目的が違う)。そして本プロジェクトの
設計の肝は、検証で回るコード=実機に載るコードを**同一ファイル**にしてあること
(`deploy/g1_mission_controller.py`)。検証に合格した瞬間、「実行できる根拠のある
出荷物」が既に手元にある。

## 3. 全体アーキテクチャ: 「1つの脳 + 台本 + 交通整理」

ニューラルネットは歩行1個だけです。着座は**台本(スクリプト)**で、両者を
**FSM(有限状態機械 = 状態の交通整理役)** が 50Hz で繋ぎます:

```
NAVIGATE ──椅子まで0.7m──▶ TURN ──向き合わせ完了──▶ ALIGN(後ろ向きに寄る)
   ▲                                                  │ 誤差4.5cm以内+向き15°以内
 レイキャストVFHで                                     ▼
 障害物回避操舵          リトライ(≤5回)◀───── SETTLE(その場足踏みで静定)
                             ▲                        │ カットゲート(下記)
                             └─条件を満たさない────────┤
                                                      ▼
                                               SIT(0.7秒で着座姿勢へ)──▶ HOLD(3秒)
```

各状態がやること:

- **NAVIGATE**: ロボットの腰の高さから21本の**レイ(光線)**を扇状に飛ばし、障害物までの
  距離を測る(疑似LiDAR)。塞がった方向を避けて空いた方向へ操舵する古典手法
  **VFH**(Vector Field Histogram)で、歩行ポリシーの「スティック」を倒す。
- **TURN**: 椅子の手前0.7mで停止し、その場で180°回頭(人間が椅子に座る時と同じ)。
- **ALIGN**: 後ろ向きに歩いて**ドック点**(座面前縁+4cm)へ。位置とヨー(向き)の
  P制御サーボでスティックを微調整。
- **SETTLE**: ドック点に「張り付く」足踏み(ステーションキーピング)。そして
  **カットゲート**——「両足接地 ∧ 足が左右に揃っている ∧ 速度が安全範囲 ∧ 体が揺れていない
  ∧ 位置・向きが許容域内」——を満たす瞬間を待つ。
- **SIT**: ゲートが開いた瞬間、ポリシーを**切って**、0.7秒かけて関節を検証済みの着座姿勢
  (股 −1.254 rad、膝 +1.611 rad、足首 +0.137 rad)へ直線的にランプ。座面が体を受け止める。
- **HOLD**: 3秒姿勢保持。最後に自動判定(高さ・姿勢・接触力)で合否を出す。

なぜ全部RL(学習)にしないのか: 歩行のような連続的バランスは学習が圧倒的に強く、
着座のような1回きりの遷移は台本+幾何の実測で十分に決まるからです。さらにこのFSMは
将来、学習データの**自動生成エンジン**(教師)として再利用されます(§7)。

## 4. 【重要】シミュレーションは現実とどう対応するのか

### 4.1 「赤い箱」は実機に付いていないが、問題ないのか?

動画でロボットの腰に見える半透明の赤い箱(骨盤ボックス)や、腿のカプセルは、
**実機に追加する部品ではありません**。答えを一言で:

> **現実世界では物理そのものが接触を「実行」してくれる。シミュレーションでは接触を
> 「計算」しなければならず、その計算のためにロボットの体を単純形状で近似したものが
> あの箱・カプセルです。**

詳しく:
- 実機のG1が椅子に座るとき、金属の尻が座面に当たる——これは現実が勝手にやってくれます。
- シミュレータで同じことを起こすには「どの形がどの形に当たるか」を毎ステップ計算する
  必要があります。見た目用の詳細メッシュ(数千ポリゴン)で接触計算をすると遅く数値的にも
  不安定なので、**箱・カプセル・球で体を近似して接触計算する**のがロボティクス標準です。
  Playground の G1 モデル自体、腿・脛・足にこの目的のカプセルを最初から持っています。
  私たちはそこに骨盤と胴体の箱を**追加**し、椅子との接触ペアを張っただけです。
- **質量・慣性・モーター・重力は一切変えていません**(総質量33.341kgのまま。
  追加形状は質量ゼロで、衝突計算にだけ使われます)。

### 4.2 本当のリスクは「近似のズレ」——そして実際に起きた

危ないのは「箱があること」ではなく「**箱が実機の体と違う形であること**」です。
本プロジェクトで現実に起きました: 当初の骨盤ボックスは底面が実機メッシュ(Unitreeの
CAD由来)より**5cm浅く**、「腿は座面に載るのに尻が座面に届かない」という、実機では
起こらない挙動を生みました。対処は**シミュレータ側を実機に合わせて校正する**こと——
メッシュの寸法を計測し、ボックス底面を実測値(ベース−0.155m)に一致させました。
教訓: **シミュレーションの結論は、モデルが実機に忠実な範囲でしか信用できない。
疑ったら実測してモデルを直す。**

### 4.3 忠実な部分/妥協している部分(正直な一覧)

| 項目 | 状態 |
|---|---|
| 質量・慣性・関節構成・モーター定数 | Unitree公式値(Playground経由)、無改変 |
| 重力・摩擦・接触物理 | MuJoCo標準、無改変。ワープ・固定・外力注入なし |
| 骨盤・胴体・腿・脛・足の対椅子衝突 | 実機メッシュに校正した近似形状で計算 ✓ |
| 歩行ポリシー | 公式学習済み(実機転移を想定して訓練されたもの) |
| **脚と障害物の衝突** | **未接続**(回避はレイキャスト+骨盤ボックスのみで強制)→ 次の課題 |
| 腕・手と椅子の衝突 | 未接続(本タスクでは接近しない) |
| センサノイズ・通信遅延 | モデル化していない(シムは理想センサ) |
| 椅子 | 座面高0.39m=G1の体格に適合させた(人間用0.45mはG1には高すぎる、§5参照) |

### 4.4 実機に持っていくまでの考え方(sim2real)

シムと実機の残差(摩擦・モーター応答・遅延など)は **sim2real ギャップ**と呼ばれ、
標準的な埋め方は: ①シム内で条件をランダム化して頑健にする(ドメインランダム化)、
②保守的な余裕を持った設計(本FSMのゲート類はまさにそれ)、③実機はLinux機で段階検証。
本プロジェクトの開ループ着座(台本)は最も実機ギャップに弱い部分なので、実機前に
RL着座ポリシー(進入状態・椅子形状をランダム化して学習)に置き換えるのが計画です。

## 5. 開発の実録 — 物理に11回殴られて学んだこと

ここが一番の教材です。**部品単体は全て検証済みなのに、繋ぐと失敗する**——統合こそが
本番でした。時系列で(各行の詳細は docs/AUTONOMOUS_SIT_PLAN.md の表とコード内コメント):

**フェーズ1: 土台づくり(個別検証)**
1. 着座の台本作り: 足首が弱い(kp=20)ため、ゆっくり座る(≥1.5秒)と必ずつま先を支点に
   前転する。**速く座る(1.0秒)+つま先を踏ん張る足首バイアス**が解。
2. 着座の許容ずれ(**バスン**=ここから始めれば成功する範囲)を実測: 位置±8cm、向き±45°。
3. 歩行ポリシーの観測103次元を正確に再現し、静止ドリフト2cm/sまで校正。

**フェーズ2: 統合v1(平らな座面)— 失敗3回**

4. ドッキング2.5cmの精度で寄せたのに転倒 → **向き(ヨー)を誰も制御していなかった**(+64°)。
5. 足踏み中にいきなり座らせたら0.4秒で横転 → 片足が浮いた非対称な瞬間だった。
6. 「安定するまで待つ」固定時間判定が揺れの山に当たる → 条件を満たすまでポーリングに変更。
   → v1成功(ただし椅子は貫通し放題の板1枚)。

**フェーズ3: 現実的な椅子(本ガイドの主題)— 失敗7回+大発見3つ**

7. 立位で腿が座面を貫通する位置関係と判明 → 接近経路を人間と同じ
   「正面→180°回頭→後ろ向きドッキング」に全面再設計。
8. **大発見①**: 骨盤ボックスが実機より5cm浅かった(§4.2)→ 校正。
9. **大発見②**: 校正したら、0.45mの人間用椅子では「前傾34°のパーチ姿勢」が物理的正解と
   判明。**身長1.32mのG1が直立で座れる座面は0.39m**。椅子をロボットの体格に合わせた
   (人間が子供用椅子を用意するのと同じ。0.45m椅子への着座は別スキルとしてRL課題に)。
10. 静定待ちタイムアウト時に位置がずれたまま座ろうとして椅子の縁に尻もち→スタック
    → 「予算外では絶対に座り始めない」を全経路に強制。
11. 足踏みが3cm/sで椅子側へ流れる → 校正済みトリムは進行方向・履歴依存だった
    → 足踏みを閉ループ(位置サーボ付き)に。
12. 着地した瞬間を「静か」と誤判定して立位が座屈 → 持続条件に → すると今度は
    **「静かな両脚支持期」はこの歩容に1〜3ティック(0.02-0.06秒)しか存在しない**と判明。
    「完璧な瞬間を待つ」戦略自体が構造的に不可能。
13. **大発見③**: ポリシーを切った後の開ループ立位は**約2秒で前方転倒する時限爆弾**
    (椅子なし・ずれゼロでも実測pitch+78°)。しかもカット時の残留速度0.1m/sを殺せず
    1秒で10cm滑空=「座面の手前の空中に座る」。
    → **立位フェーズを丸ごと廃止**。着地瞬間から**直接0.7秒で降下**し、残った運動量は
    座面そのものに殺させる。速度ゲートは**非対称**に: 椅子から遠ざかる速度は厳禁
    (空中に座る)、椅子へ向かう速度は許容(座面が受け止める安全方向)。
    → **v2成功**: 着座高さ誤差0.1mm、ピッチ0.0°、支持力229N(骨盤+両腿の人間型荷重)。

**メタ教訓(次にあなたが何か作る時のために)**:
- 推測で直さず**必ず計測する**(このログの対策は全部、テレメトリの数字から導かれた)
- 失敗は隠さず記録する(失敗の表が一番価値のある成果物)
- 「シムが変な挙動をする」と感じたら、シムを疑う前に**モデルの実機忠実度**を疑う(§4.2)
- 統合テスト(E2E)でしか出ないバグが本体。部品の検証だけで安心しない

## 6. 自分で動かす・いじる

```bash
# 基本実行(§0)
.venv-rl/bin/python training/g1_walk_to_sit.py

# 環境変数
G1W2S_NOGIF=1   # レンダリング無し(物理は同一、~30秒で判定だけ出す)
G1W2S_DEBUG=1   # 詳細テレメトリ(状態ごとの座標・速度・接触力が0.1秒刻みで出る)
```

いじりどころ(全部 `training/g1_walk_to_sit.py` の定数):
- `OBSTACLES`: 障害物の位置・形・色。動かして回避を観察してみる
- `SEAT_WORLD` / `CHAIR_YAW`: 椅子の場所と向き
- `ALIGN_TOL` / `YAW_TOL` など: ドッキングの厳しさ(緩めると何が起きるか見ると勉強になる)
- 椅子の形状そのもの: `training/g1_sit_env.py` の `REAL_*` 定数(単一情報源)

実験の作法: 変更 → `G1W2S_NOGIF=1` で高速確認 → 失敗したら `G1W2S_DEBUG=1` で数字を見る
→ 原因が分かってから直す。本プロジェクトの全進捗はこのループでできています。

注意: 物理は決定論(同じ条件なら毎回同じ結果)です。1回成功=その条件で成功、であって
あらゆる条件での頑健性ではありません(次の課題参照)。

## 7. 次の課題(新規参加者ができること、易しい順)

1. **配置ランダム化スイープ**: 椅子・障害物・開始位置を乱数で振って成功率を測る
   (N=50)。失敗ケースが次の改善箇所を教えてくれる。レンダリング無しなら数分で回る
2. **脚×障害物の衝突接続**: `g1_sit_env.ROBOT_LEG_GEOMS` と障害物のペアを張る。
   現在の最小クリアランス0.11mでは脚が掠るため、VFHの`SAFE`/`WIDEN`の再調整とセット
3. **知覚の自律化**: 現在のVFHは障害物のグループ番号を「知っている」(特権情報)。
   深度カメラレンダリング→疑似LiDAR化は `vision_nav.py`(旧スタック)で実証済み、移植する
4. **RL着座**: 進入状態と椅子(高さ0.35-0.50m=人間用椅子パーチ含む)をランダム化した
   着座ポリシーを学習。`g1_sit_env.py` にRL環境(G1Sit)が定義済み。M5 MaxのCPUだけでも
   20Mステップ≈15-30分(実測ベース)
5. **音声→着座**: 「椅子に座って」→ Whisper → ローカルLLM → このFSM、のパイプラインは
   別スキル(voice_chair.py)に存在。実行器を本E2Eに差し替える

## 8. ミニ用語集

| 用語 | 意味 |
|---|---|
| DOF(自由度) | 独立に動く関節の数。G1は29 |
| qpos / ctrl | 体の状態(位置+関節角)/ モーターへの目標角度指令 |
| ポリシー | 観測→行動を毎ステップ計算する関数(ここではニューラルネット) |
| ONNX | 学習済みニューラルネットの携帯フォーマット。CPUで実行可能 |
| RL(強化学習) | 報酬を最大化する行動を試行錯誤で学習する手法。歩行ポリシーの出自 |
| FSM(有限状態機械) | 「今どの段階か」を管理し、段階ごとに制御を切り替える仕組み |
| VFH | レイで測った障害物分布から空いた方向を選ぶ古典的回避手法 |
| レイキャスト | 光線を飛ばして最初に当たる物までの距離を測る計算。疑似LiDAR |
| キーフレーム | モデルに保存された基準姿勢(ここでは knees_bent =膝曲げ立位) |
| バスン(basin) | そこから始めれば成功する初期条件の範囲(吸引域) |
| トリム | 指令ゼロでも生じる定常ドリフトを打ち消す補正指令 |
| contype/conaffinity/pair | MuJoCoの衝突フィルタ。pairは「この2形状だけ衝突させる」明示指定 |
| 衝突プロキシ | 接触計算用の単純近似形状(箱・カプセル)。§4参照 |
| sim2real | シミュレーションと実機の差、およびそれを埋める技術全般 |
| ドメインランダム化 | シム内で物理条件を乱数で振って頑健なポリシーを学習させる手法 |
| 開ループ/閉ループ | センサを見ずに台本を再生する制御/センサで補正し続ける制御 |
