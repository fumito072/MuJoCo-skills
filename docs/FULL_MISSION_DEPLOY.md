## 0. ゴールと到達点

ミッション: 部屋の反対側から、**障害物を自ら検知・回避**して実在の椅子
(3階講堂遠隔操作席)の前まで歩き、**0.22m のフットレスト台に登り**、**着座**する。
全てシミュレーション内で連続1ロールアウト、Mac ローカル(GPU/クラウド不要)。

実行:

```bash
.venv-rl/bin/python training/g1_full_mission.py          # フルミッション(GIF付き)
G1FM_NOGIF=1 .venv-rl/bin/python training/g1_full_mission.py   # 高速判定
```

アーキテクチャの核心: **シムで検証されるコード=実機に載せるコード**。
ミッション制御は `deploy/g1_mission_controller.py`(numpy+onnxruntime のみ、
MuJoCo 非依存)に実装され、`training/g1_full_mission.py` はそれを MuJoCo に
接続する薄いアダプタ。実機側アダプタ(`deploy/run_on_robot.py`)は同じ
コントローラに実センサを繋ぐだけ。

```
                 ┌─ training/g1_full_mission.py(シム・アダプタ)── MuJoCo 物理
state dict ──▶ deploy/g1_mission_controller.py ──▶ target/kp/kd
                 └─ deploy/run_on_robot.py(実機アダプタ)──── unitree_sdk2py
```

## 1. ミッション FSM

```
NAVIGATE(歩行ONNX+VFH障害物回避、ゴール=台手前1.25m)
  → TURN(床上で180°回頭 — 台上では回頭不能のため先に向きを作る)
  → BACKUP(PI ステーションキーピングで後ろ向きに台際 y0.67 へドッキング)
  → CLIMB(★RL方策: 後ろ向き段差登り、SITモード剛性ゲイン kp300)
  → SIT(検証済み剛性降下レシピ: 立位0.4s→降下0.6s→静定0.8s→姿勢1.5s→保持3s)
```

各部品の出自: 歩行=公式 playground 29DOF ONNX(無改変)/ VFH=既存スキルの実証済み
パラメータ / BACKUP の PI サーボと着座レシピ=実測検証済み(docs/AUTONOMOUS_SIT_PLAN.md
v3)/ **CLIMB=本フェーズで新規にRL学習**(§3)。

## 2. なぜ「後ろ向きに登る」のか(設計判断)

- 座るには台上で「背を椅子に向けて」立つ必要があるが、**台は0.6×0.3mで歩行・
  回頭は不可能**(実測: 歩行方策のコールドスタートだけで台から落ちる)
- 前向きに登ると台上で180°ピボットが必要になる → 詰み
- **床で回頭してから後ろ向きに登れば、台上での向き変えが一切不要**
- 後ろ向きステップは人間の手作業振付では困難だが(§3)、RLには前後の区別は
  単なる座標の符号 — 学習にとって難度は同じ

## 3. Phase 3: 段差登り — スクリプト14連敗 → RL

### 3.1 スクリプト方式の敗北記録(全て実測、教材として保存)

剛性ゲイン+ウェイポイント振付+足首/股関節の CoM-PD フィードバックまで投入して
14回失敗。本質的な敗因は3つの連成:

1. **遊脚質量の反作用**: 脚(~5kg)を振ると CoM が逆方向へ逃げ、片脚支持の
   支持多角形(足1枚=±3cm)を即座に割る
2. **ベース後退**: CoM を支持足上に保つ制御は、脚を前に出すと**胴体を後ろに
   下げて釣り合わせる**(物理的必然)→ 着地点が届かない
3. **横ロールの蓄積**: 片脚支持の1-2秒間に足首・股のフィードバック権限
   (足首ロール±0.26rad、CoP=足幅)が飽和する

→ 結論: 0.22m 段差の片脚支持遷移は**閉ループ全身協調**が必要 = RL の出番。
(g1-isu が全タスク一括RLで3.5Mステップ未習得だったのに対し、本実装は
**登りだけを切り出した専用タスク+密な報酬**で学習)

### 3.2 RL タスク設計(training/g1_climb_env.py)

- 行動: 脚12関節の位置目標(50Hz、±0.45rad、kp300/kd8)
- 観測52次元: 重力・ジャイロ・体速度・基準高・ヨー誤差・**目標点への体座標
  ベクトル**(実機では椅子測量+オドメトリ)・脚関節位置/速度・足接触・前回行動
- 報酬: ポテンシャル形(目標点+台上高への前進)+台上足接触+微小生存
  −姿勢/ヨー/行動レート/関節速度ペナルティ、成功+100/転倒−20
- **チェーン接続を見据えた初期化ランダム化**: 本プロジェクト最大の教訓
  (歩行マーチからの引き継ぎ過渡が全てを壊す)を環境に焼き込み — スポーンに
  基準速度±0.15m/s・関節速度±1rad/s・関節角±0.12radのノイズ
- **報酬ハッキングと対策**(実際に起きた): 初回学習は「段差の縁に腰掛けて
  生存ボーナスを満額回収する」局所解に収束。対策=生存ボーナス1/5+
  **足以外の身体と椅子の接触にペナルティ**+高さ項強化
- 学習: SB3 PPO、M5 Max CPU 10並列 **~9,000 steps/s**(クラウド不要)

### 3.3 結果(正直な現状: 部分達成)

**36Mステップ・6回の報酬/カリキュラム手術の結果**:
- 近接逆カリキュラム(RSI)領域からの成功率 **35-45%**(成功+200の価値は学習済み)
- 段の縁への「つま先掛け片足ホールド」を自力発見し無期限維持(登りの~70%)
- **床スポーンからの完全登攀は 0/20 — 未達**。つま先掛け→深い足設置→第二足移行の
  価値伝播が3つのカリキュラム設計でも床まで届かなかった
- フルミッションは転倒ゼロで CLIMB タイムアウトまで進行(assets/g1_full_mission.gif
  =現状フロンティアの記録: 回避0.186m→回頭→後退ドッキング→登り試行→ホールド)

**スクリプト側の収穫**: 25回の試行から**検証済みプリミティブ「縁着座」**を獲得
(後ろ向き剛性降下で台の縁に安定着座、base z 0.375/pitch 0° —
training/g1_edge_sit_probe.py)。台上で座位から足を置く空間が無いことも幾何学的に確定。

**前向き vs 後ろ向きの A/B 検証(2026-06-11 追試)**: 「後ろ向きだから失敗するのでは」
という仮説を検証 — 環境を前向き接近(成功条件=台上で+y向き立位、回頭は方策の自由)に
再定義し、回頭はしご型RSI(台上 yaw −90°→+90° の中間状態90個+前向き橋50個)で
ゼロから14M学習。結果: RSI領域成功 19-25%(後ろ向きと同等)、**床スポーン 0/20(同じ)**。
前向きは床からの台への足掛けが速い(0.5-1.4秒で片足設置)が、その後の体重移行で同様に
転倒。→ **結論: 方向の問題ではなく、床→台の片脚支持遷移の「発見」そのものが
CPU規模PPO+本カリキュラムの壁**。回頭は問題にならない(RSIで両方向とも学習可能)。

**次の登攀候補(優先順)**:
1. **GPUスケール学習**(MJX/Isaac で 10^8 ステップ級+大規模並列の探索量 —
   この種の単発スキルの標準的な解かれ方)+ 適応的RSI後退
2. **肘掛け手押しスクート**: 検証済みの縁着座から手で肘掛けを押して体を持ち上げ
   深部へ(hand_collision×椅子ペア追加+腕振付。人間と同じ手順)
3. ホールド→橋状態を繋ぐ**第二方策**(2方策チェーン)

### 3.4 手ブレース実験 — 「前傾して肘掛けに手をつく」(2026-06-13)

発案はユーザー: 「手で肘掛けの部分を持って状態を前傾にしてから前足を上げて段を
登るのはどうか」。Colab GPU の空き待ちの間に Mac のスクリプト+CoM-PD 制御
(`training/g1_handbrace_probe.py`)で 21 イテレーション検証した。

**獲得した検証済みプリミティブ — 「4点ブリッジ」**(本実験の最大の成果):

| 段階 | 実測値 |
|---|---|
| 三脚リーン | 前傾 20°、両手が肘掛け前面に接触(各 5-10 N)、2 秒静止 |
| **4点ブリッジ** | **前傾 28.5-34°、両手 40-70 N、つま先接地、1-2 秒静止(再現可)** |
| 深部キャッチ | 前傾 64° で両手 144/93 N(体重の約 7 割)の懸垂を一度観測 |

デモは `python training/g1_handbrace_probe.py` で再現(判定 `BRIDGE HELD`、
状態は `BRIDGE_T=7.0` で `training/g1_bridge_state.npz` に出力、qvel ノルム 0.08)。

**鍵だった発見(全て実測)**:
- **手首剛性が成立条件**: 純正 kp=2 の手首はフニャフニャで、押すと手が転がって
  細い肘掛け上面から滑落する。kp=80(実機のモード別ゲインに相当)で手が
  「剛体の支柱」になりブリッジが初めて成立した
- 直立床立位から肘掛け先端には手が届かない(前傾 25° が必要だが、支え無し
  足首の限界は 18°)→ 接触は肘掛け**前面斜面**で起き、座面(z 0.635、水平)が
  深部の受けになる
- 足首ピッチの符号: **負=背屈=前傾**(着座レシピの +0.137 はスクワット文脈)。
  waist_pitch も負=前屈
- CoM-PD のピッチ補償は意図的な前傾と戦う → ウェイポイント別 `nopitch` フラグで
  「手が受け止める前提の制御された倒れ込み」を実装

**未達と結論**: ブリッジから片足を持ち上げる遷移は全パターン(高速スイング/
つま先ドラッグ/荷重移動後)で失敗。原因は一貫していて、**握れない手
(丸カプセル×丸い肘掛け縁=点接触)の摩擦コーンを、脚スイングの反動が必ず破る**。
これは時刻表ベースのオープンループでは原理的に救えず、接触力フィードバック=
RL が要る — そこで本実験の成果を次の GPU 学習に注入した:

- `g1_climb_mjx_env.py` に**簡易肘掛け+座面ボックス(手のみ衝突)**、
  **腕モードゲイン(肩肘 kp150 / 手首 kp80)**、**ブリッジ開始モード
  (リセットの 25% を実測ブリッジ状態から開始する RSI)**を追加
- 検証側 `g1_climb_play.py` もフル椅子で手ペア+腕ゲインを一致させた
  (ブレースを学んだ方策が検証で不当に落ちないように)
- 一番難しい「ブレースに到達する」までをスクリプトの実測値が与え、PPO は
  「ブレースから登り切る」だけを学べばよい — 報酬は無改造(ハック面を増やさない)

### 3.5 片足立ちカリキュラム — 「まず90°片足立ちの体幹を獲得させる」(2026-06-13)

発案はユーザー: 人間は片足を上げる前に軸足へ重心を乗せる — まず90°片足立ちを
学習させ、体幹を獲得してから足を下ろす方が良いのでは。この発想は §3.1 の実測
失敗(遊脚反動・横ロール飽和)と正確に一致する。スクリプト10イテレーションで
検証した。

**デモ**: `assets/g1_oneleg_attempt.gif`(`training/g1_oneleg_probe.py` で再現)—
重心移動→90°タック(足z 0.28-0.37m)→**約0.3秒の片足立ち→転倒**。成功デモは
まだ無い(現状の最良試行を正直に記録)。成功版は モードD 入りGPU学習の方策で
撮る予定。

**実測で確定したこと**(計16イテレーション):
- **股関節ロール戦略は機能する**: 両股関節ロール負で骨盤が軸足(左)上へ移動。
  足首ロールPDのみ(±0.26 clip)では5cm止まりだったCoM移動が、股関節で12cm出る
- 符号マップ: 股関節ロール **負=左へ**(±0.15 で base x ∓0.22m)、waist_roll
  **正=体幹左傾**(±0.15 で base x ±0.03m)
- CoM は軸足中心 ±1cm まで到達、遊脚は90°タック(足 z 0.37m)まで上がり、
  **最長0.36秒の片足立ち**を記録 — 状態自体は到達可能
- **未達の理由**: 横方向の体重移動は「雪崩」— 閉リンクの脚押しで加速し、中心
  通過時に ~8cm/s。タイマー遷移では捉えられず、状態ゲート+ブレーキ区間を
  入れても開ループの綱渡り(v2右転倒↔v3左転倒、間が無い)。手調整PDの帯域と
  協調を超えており、**まさに学習で解くべき問題**(ユーザーの提案どおり)
- 続報(計16回): 状態ゲート(3.5cm地点で発火)+ブレーキ区間で**重心を軸足
  ±1cmに準静的に静止**させることに成功。接地判定の罠も発見(接地中の足は
  z≈0.01 — 閾値0.06では単脚検出が0.3秒遅れ、その間に重心が逃げる)。しかし
  そこから足を浮かせると4種類の転倒モード(右並進/左並進/右回転/反作用結合)
  を全て踏み、股関節フィードバックの符号を反転しても別モードで倒れる —
  単脚支持では股関節トルクが「位置」と「姿勢」を同時に直せない(トルク対の
  反作用)、capture point 制御の領域=**手調整PDでは原理的に届かない**ことを
  確認。軸足足首を柔らかく(kp40)しても結果不変

**実装 — G1ClimbBox にモードD追加**(リセットの15%): 段差の縁で片足立ち状態
(軸足上にCoM、遊脚は50〜100%の90°タック=カリキュラム勾配、左右ランダム)から
開始。上げた足は台まであと一歩 — 床スポーン(モードA)が一度も到達できなかった
「持ち上げ直後」の状態を価値連鎖の中継点として直接与える。
リセット配分: ブリッジ25% / 片足立ち15% / 台上25% / 床35%。
ブートストラップセルは新env込みで再生成済み。

### 3.6 片足立ちを Mac + PyTorch で**学習成功**(2026-06-14)

ユーザーの方針「このMacでPyTorch学習し、片足立ちを実現する」を実行 — そして
**成功**。手調整(§3.5)が原理的に届かなかった単脚支持バランスを、**RLが獲得した**。

- 専用環境 `training/g1_oneleg_env.py`(平地・椅子なし・Gymnasium):2足立ちは
  脚SITモード剛性 kp300 で静的安定にし(無料化)、報酬を「直立＋遊脚を0.18mまで
  上げる＋軸足上にCoM＋片足クリーン状態に+2.0/step」に集中。成功=片足立ちを
  連続1.5秒以上保持。軸足は左右ランダム。行動は全身29DOF(腕もバランスに使う)
- `training/g1_oneleg_train.py`(SB3、**device=cpu の PyTorch**、PPO、24環境、
  SubprocVecEnv＋VecNormalize)。PPO/SACをフラグで切替可(A/B用)
- **実測**:Mac単体で **~14,800 fps**(24環境)、15Mステップ=**約17分**で学習完了。
  成功率の立ち上がり 1.5M:0% → 2.7M:4% → 9M:87% → 15M:**94%**
- 決定論的評価(`g1_oneleg_play.py`、20エピソード):**15/20成功**、保持中央値
  3.23秒、**最高5.96秒=全6秒エピソードを一度も倒れず完走**。右軸足は鉄壁、
  左軸足はやや不安定(非対称が残存)。デモ `assets/g1_oneleg.gif`

**戦略的な意味**:これは前章までの議論(パターンB=Mac単体学習)の**実証**でもある。
GPU不要・NVIDIA不要で、扱いやすいタスクなら18コアCPUのMacが訓練機として十分機能する
ことを、片足立ちという登攀の核心スキルで示せた。

**device=mps はこのタスクでは逆に遅い(実測 2026-06-14)**:同じ片足立ち学習で
cpu **14,800 fps** vs mps **7,765 fps**(MPSが約2倍遅い)。MPSは本物のGPUだが、この
ワークロードは(a) CPU物理シミュレーション と (b) 1イテレーション512回の小バッチ
推論(GPU転送オーバーヘッドが支配)で律速し、MPSが勝てるのは大バッチ勾配更新だけ
=全体の一部。ユニファイドメモリ128GBは本物だが使用量<1GBで無関係。→ CPU が正解。

**v3「静止版」(2026-06-14)**:v1の方策は重心が踵+永遠にヨー回転する極限周期
バランスだった(静止していない)。報酬を再設計 — v1の片足立ち誘因は温存しつつ、
①片足ボーナスを静けさで割り増し(`3.0*exp(-0.8*spin)*exp(-1.5*yaw_drift)`)、
②控えめな回転/並進/ヨードリフト罰、③**膝を前方に上げる誘因**(踵重心の是正)。
失敗した中間版(v2)の教訓も記録:静止罰を強くしすぎると「安全な両足立ちで静止
報酬を稼ぐ」局所最適に落ち成功率0%(ep_rew 400で頭打ち)→ 片足ボーナスが両足立ち
を常に上回るバランスが必須。**v3結果(決定論的評価20本)**: 19/20成功、保持中央値
**5.94秒=全6秒完走**、保持中スピン平均0.91 rad/s(最良0.5前後、v1の永続回転から激減)、
向きを保持。腕を上げてのバランスは人間同様の正当な戦略。完全静止(0 rad/s)は劣駆動
バランスゆえ困難(人間も揺れる)が、ユーザー指摘の踵重心・永続回転は実質解消。

**v4「段差対応版」(2026-06-14)**:ユーザーがv3のGIFを見て「段差を登るには弱い —
片足を90度に垂直に上げても体幹がブレていないのが必要」と指摘。これは正鵠。v3は
前傾＋腕flailの“倒れない”recovery姿勢でリフトも低かった。v4で報酬を再設計 —
①リフト目標 0.18→**0.30m**、保持ゲートを実段差の **0.22m クリア**に厳格化、
②股関節の前方屈曲(膝を〜90度へ)を加点、③**腰を中立に保つ罰**(前傾の根絶)、
④腕中立罰(flail根絶)、⑤直立項を強化、⑥clean ゲートに「0.22m超＋腰中立」を要求。
30Mステップ=約96分(~5,200 fps、24環境)で学習、最終成功率97%。**v4結果(決定論的
評価20本)**:**20/20成功**、保持中央値**5.94秒=全6秒完走**、**スイング足高 0.27–0.29m
(実段差0.22mをクリア)**、**体幹傾き 2.8〜9.4°(v3の前傾＋腕振りは解消)**。
正直な残課題:スピンは 1.26 rad/s と v3(0.91)よりむしろ増えた — ただし向き(yaw)は
保持しており、これは「高く上げた足を支える能動的バランス微振動」(高リフトの本質的
コスト)で、v3の正味回転とは別物。左右差は残存(右軸足3°＜左軸足8°)。

**ユーザー要求2点(高リフト＋ブレない体幹)は達成。** ただし「平地の静的片足立ち」と
「実際に足を段上へ着地させる動的ステップ」は別スキルであり、**真の検証は climb タスク
への組込み**。次は ① 左軸足の非対称を詰める、② この v4 方策を段差登りの初期化/
カリキュラムに接続する。

## 4. 正直な注記(シムの妥協点)

| 項目 | 状態 |
|---|---|
| 障害物回避の物理 | VFH+骨盤ボックスのみ(脚は障害物を貫通可能 — クリアランス計測で担保) |
| 椅子・自己位置 | 既知座標(特権)。実機は測量+オドメトリ、知覚化は次トラック |
| クッション | 剛体近似(実物は沈む=実効座面が低い → シムが保守側) |
| センサ | 理想(ノイズ・遅延なし)→ 実機チェックリスト対象 |
| CLIMB方策 | 学習分布(スポーン±4cm/±0.10rad+速度ノイズ)外の状況は未保証 |

## 5. 実機 Linux への展開(deploy/)

`deploy/README_DEPLOY.md` が正典。要点:

1. **バンドル**: コントローラ+config.json+ONNX2個(歩行/登り)。
   ロボット側依存は `numpy onnxruntime unitree_sdk2py` のみ(torch不要 —
   `export_climb_onnx.py` が正規化込みでONNX化)
2. **アダプタ**: `run_on_robot.py` は 500Hz lowcmd ループ+50Hz 判断+線形補間の
   unitree_rl_gym 慣行構造。**TODO(HW) 6箇所**(SDK配線・関節マップ・推定器・
   椅子フレーム自己位置・LiDAR整形・E-stop)は現地でしか書けない/検証できない
3. **段階投入**: ゲイン校正(吊り)→ SIT単体 → CLIMB単体(モック段差)→
   歩行系 → フルチェーン。各段階ハーネス+E-stop
4. **「ぶち込むだけ」の正確な意味**: 制御ロジック・方策・校正値はシム検証済みの
   まま持ち込める。現地作業は上記アダプタ配線と安全検証であり、
   **制御設計のやり直しは発生しない**(それがこの構造の価値)
